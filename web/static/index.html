Target decision

Two paths are possible and the client chooses. Keep Oracle on Amazon RDS, or leave Oracle for PostgreSQL and end the licence. The rules assess both from the estate's own evidence: what would block each path outright, and what would cost effort. Then a proposer suggests an instance class and storage, and a deterministic rules engine overrules it where they disagree.

Measured utilization — optional

A catalogue scan cannot produce utilization percentiles — there is no history to take a percentile of. Without a feed this sizing is a capacity floor, not a load-derived recommendation. An AWS OLA / DB OLA, Migration Evaluator or monitoring export supplies it.

Migration path

A blocker is a feature the target engine cannot express at all, so the path is refused rather than warned about. Effort is work with a known shape. The stored-code figure is the one that decides this in practice, and it is measured by Phase 4b compiling the code for real — not estimated.

Chosen target
RDS for PostgreSQL has no editions and no licence model. The Oracle feature usage that decides Enterprise versus Standard Edition 2 — and the processor licences that follow from it — has no meaning here. That is the commercial case for this path, and the cost of it is the stored code above.

Build the target's schema

Tables, keys, checks and indexes for PostgreSQL, generated from what discovery recorded. DMS would improvise this — it creates missing tables with a fixed mapping that turns every NUMBER into numeric, and creates no constraints and no indexes at all. Every statement here is executed on a real PostgreSQL and rolled back. This phase applies nothing.

The order, and why it is not alphabetical

Constraints and indexes come after the load. Validating a foreign key row by row during a bulk insert is the slowest possible way to do it, and an index maintained during a load is rebuilt far faster afterwards. This is the same order Phase 7's Data Pump path uses for the homogeneous case.

Convert the application's SQL

The Oracle SQL embedded in the application, not in the database — AWS SCT never reads this, because it inspects a schema and these statements live in mapper files in a source repository. Extracted, routed by construct, rewritten rules-first, and gated the same way stored code is. This phase applies nothing.

What is scanned

MyBatis <if>, <where> and <foreach> tags are kept: stripping them yields SQL that parses and is not the SQL the application sends. ${…} stays interpolated — rewriting it to #{…} turns a column name into a bound literal and the query fails at runtime, not at conversion.

What proves a rewrite
Checking the target…

Two separate questions, and merging them is how a converter passes while being wrong. Parse asks whether the target accepts the statement — cheap, one connection. Result asks whether it returns the same rows as the Oracle original over the same data — and it is the only check that catches a ROWNUM pagination rewrite that parses perfectly and returns a different page. Without a target both report blocked, never a silent pass.

Migrate

      
How the data moves depends on the target Phase 3 chose. Oracle to Oracle uses Data
         Pump over S3: one dump, loaded directly. Oracle to PostgreSQL uses AWS DMS,
         because Data Pump writes an Oracle-only format that PostgreSQL cannot read — and DMS is
         also what makes change data capture, and so a short cutover, possible at all.

    


    
    

      

        

          

            
AWS Database Migration Service

            

              A replication instance reads the source and writes the target. It bills by the
              hour for as long as it exists, whether or not a task is running — unlike Data
              Pump, which finishes and stops. Planning below is free and creates nothing.

Validate

      
Five levels, from it exists to it behaves. Every finding is marked
         match, expected difference with the reason it is correct, mismatch, or
         not comparable when one side cannot be read — which is never counted as a match.
         Only mismatches fail the phase. Nothing is written to either database: every statement is
         a SELECT.

    


    

      
Oracle and PostgreSQL do not store the same value the same way.
        Comparing raw bytes would report a failure on every numeric and every padded column of a
        perfect migration. So each row is reduced to a canonical text form on both sides
        first — trailing zeros stripped, CHAR padding trimmed, timestamps in UTC, and Oracle's
        empty-string-is-NULL given the same marker as a PostgreSQL NULL — and the same MD5 is
        computed over that. Levels 2 and 5 do not run: column types are deliberately
        different, and invalid objects and grants are Oracle catalogue concepts. What survived is
        measured by levels 3 and 4, which are the ones that answer whether the data is
        intact.

Cutover

         clear it. Building the certificate changes nothing.
